# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

An Arduino-based split-flap display. Firmware built with **PlatformIO** — each sketch has its own `platformio.ini` and builds from the CLI. Host-side unit tests for pure-logic helpers live under `firmware/v1/ESPMaster/test/`. CI in `.github/workflows/build.yml` builds every firmware project and runs the native test suite.

**Firmware status:** the shipping firmware is the v1 stack under `firmware/v1/` — `ESPMaster/` (ESP8266 master) + `Unit/` (Arduino Nano per-flap). This is the actively-maintained firmware. The v2 stack is being built per the phased plan in epic #183: `firmware/v2/Master/` is the Phase 1 ESP32-S3 port (#58) — an S3 devkit speaking the same I2C protocol to **unchanged v1 units**, plain `.cpp` (no `.ino` concat), console on native USB-CDC. Settings live on NVS (`Settings.h` over the `SettingsStore` seam, #185). The v1 web surface is ported (#186): `data/` + `build_assets.py` bake the UI into PROGMEM exactly like v1, endpoints live in `WebEndpoints.cpp` on the `esp32async/ESPAsyncWebServer` stack (unported services answer 501). WiFi (#188): credentials live in our Settings NVS (`wifiSsid`/`wifiPass`; esp_wifi storage stays RAM — `WiFi.persistent(false)` everywhere, no SDK-sector black box, so v1's persistent-before-disconnect foot-gun class doesn't exist on v2); join/portal supervision is the pure `WifiPolicy.h` state machine (30 s join → 300 s `<name>-setup` portal → reboot-retry, v1 timings) executed by `WifiService.cpp` from `netTask`; the portal is hand-rolled on the same async server (`data/portal.html`, self-contained + DNS catch-all + `onNotFound` redirect — no WiFiManager dependency) and `webEndpointsStart()` is idempotent, called by whichever netif comes up first (portal AP or STA); mDNS registers on join. OTA (#190): `POST /firmware/master` keeps the v1 wire contract (multipart + mandatory `?md5=`, optional `?v=`); `Update` writes the inactive A/B slot and the image boots `PENDING_VERIFY` — a strong `verifyRollbackLater()` in `OtaService.cpp` defers the Arduino core's auto-confirm, and `otaHealthConfirm()` (first netif-up, portal or STA) cancels rollback; `/settings` verdict fields (`lastFlashResult`/`otaReverted`) are synthesized per-boot from `esp_ota` state (`OtaStatus.h`, pure) and never persisted — only `intendedVersion` lives in NVS. Clock/NTP (#192): `clockServiceApplyTz()` = `configTzTime(settings.timezonePosix, pool.ntp.org)`, applied at boot + on join + rebootless on a timezone POST (v1 #48 parity); `clockTask` (core 1) is the 1 Hz mode ticker whose brain is pure `ClockPolicy.h` — `decideClockTick()` dedups against the `DisplaySnapshot` text plus an in-flight `lastQueued` marker (one command per minute in clock mode, not per second), clock mode is gated on `time() >= 1e9` so an unsynced clock holds content instead of flapping 1970 times, and content comes from `webDisplayContentSnapshot()` (mode + runtime-only `inputText`, never persisted). Its `[env:native]` mirrors v1's (same ArduinoFake caveats); v2 Python tests: `python -m pytest tests/` from `firmware/v2/Master`. The pure-logic headers there are **copies** of their v1 counterparts, not shared includes — v1 stays stable for OTA maintenance while v2 diverges; fix bugs in both if one is found while both trees are alive.

v2 task architecture (#187, spec in `docs/superpowers/specs/`): dual-core FreeRTOS decomposition in `Tasks.cpp` — display domain on core 1 (`displayTask` will own I2C exclusively), network domain on core 0. Rule: web/MQTT code never touches display state directly — enqueue a `DisplayCommand` (params baked in by the sender), read back mutex-copied `DisplaySnapshot`s. Large buffers via `largeAlloc()` (PSRAM-preferred). Hardware: N16R8 devkit — **GPIO 35/36/37 are eaten by octal PSRAM, never assign them**. Status LED (#199): the devkit's WS2812 on GPIO 48 — pure `StatusLedPolicy.h` + `StatusLed.cpp` glue ticked from netTask (portal/join/OTA state colors, connected = dim breathing green); the boot banner prints partition diagnostics (#198). Custom partition table `partitions_splitflap_16MB.csv` (immutable over OTA); `board_upload.arduino.boot_app0` in `platformio.ini` must stay in sync with the CSV's otadata offset (the prebuilt-Arduino builder otherwise hardcodes 0xe000) — both invariants plus the #193 layout are pinned by `tests/test_partition_table.py`. Factory rescue slot (#193): a 2 MB `factory` app partition sits after `coredump` and the bootloader's factory-reset config (GPIO 4 low for 5 s through reset) erases **otadata only** — never nvs, WiFi credentials must survive a rescue; GPIO 4 is thereby reserved for the future carrier's reset button (`PCB/v2/README.md`). Rescue app (#195): `firmware/v2/Rescue/` is the break-glass image for that slot — a standalone PlatformIO project (own trimmed `build_assets.py` bake, same pioarduino platform + `custom_sdkconfig`; `CONFIG_BOOTLOADER_APP_ROLLBACK_ENABLE` is load-bearing app-side so images armed FROM rescue still boot `PENDING_VERIFY`). It shares nothing compiled with Master except the partition CSV: `RescueOta.h`/`RescueIdentity.h`/`RescueWifiPolicy.h`/`RescueSlots.h`/`RescueSlotRecord.h` are trimmed **copies** (natively tested, `pio test -e native` + `python -m pytest tests/` from `firmware/v2/Rescue`) so Master refactors can never change a bench-proven rescue image. Boot: NVS read-only → 30 s STA join else `<name>-rescue` AP (open, captive redirect; Ap/Online are terminal — rescue never self-reboots) → page with slot inventory, upload-a-bin to app0 (same `?md5=` wire contract), and `/rescue/exit` (most-recently-confirmed-slot re-arm). Exit ranking (#200): the app-descriptor `date`/`time` (and `version`) freeze at framework-assembly time under pioarduino hybrid builds — every image from the same framework cache carries the same stamp, so it can't order images. Instead Master stamps a per-slot NVS confirm record on first netif-up (`slotRec0`/`slotRec1` in the shared `splitflap` namespace, format `1|<seq>|<sha256 hex>|<git rev>`, pure `SlotRecord.h` ↔ parse-only copy `RescueSlotRecord.h` — wire-contract-like, version it on change); rescue accepts a record only when its sha256 matches the slot's actual image (`esp_partition_get_sha256` both sides) and ranks by seq (= confirm recency, so deliberate downgrades win), confirmed-beats-unconfirmed, descriptor stamp as last-resort fallback. **Never `pio run -t upload` the rescue project** — install via Master's `POST /firmware/rescue` (raw `esp_partition` write to factory, `FactorySlot.cpp` — flash sector 0 is held back in RAM until the MD5 verdict via pure `FactoryChunkPlan.h`, so a torn/interleaved upload can never leave a bootable-looking header; never touches otadata) or `esptool write_flash 0x830000`; enter via GPIO 4 or `POST /firmware/rescue-boot` (otadata erase + reboot, 409 while an install is in flight or the factory image doesn't validate — doubles as the periodic "prove it still boots" test). Native bootloader rollback is on (`custom_sdkconfig` → pioarduino hybrid compile: first build slow; `managed_components/`, `sdkconfig.*`, `.dummy/` in the project dir are generated IDF artifacts, gitignored). **Do NOT port v1's OTA verdict machinery** (RTC cookie / sketchMd5 compare) — the S3's A/B boot makes it obsolete; use `esp_ota_*` state APIs and the core's weak `verifyRollbackLater()`/`verifyOta()` hooks instead. The v2 **PCB** design docs under `PCB/v2/` were re-scoped by the same epic (unit board is the only planned custom PCB).

## Architecture

Sketches that make up the system:

- **`firmware/v1/ESPMaster/`** — ESP8266 (ESP-01) master firmware: async web UI (PROGMEM via `build_assets.py`, no on-device filesystem), WiFi via SDK-persisted credentials + `ESPAsyncWiFiManager` captive-portal fallback (no compiled-in credentials), NTP clock logic, I2C bus master. Entry point `ESPMaster.ino`; feature areas are sibling `.ino` files concatenated into one TU at build time (`Service*`, `Helpers*`). Pure-logic helpers are header-only and natively tested (`MqttHelpers.h`, `MdnsDiscovery.h`, `SettingsValidation.h`, `DeviceIdentity.h`, `DisplayWidth.h`); `ESPMaster.h` holds prototypes the Arduino preprocessor can't auto-generate. Web UI = three hash-routed tabs (Display / Settings / Maintenance); per-card saves POST only their own fields with `ajax=1`, and the handler gates every field on a "provided" flag so partial posts can't clobber absent ones. Async-context rule: handlers stage, `loop()` mutates — e.g. `POST /mqtt/discover` only arms a flag; the blocking `MDNS.queryService()` runs from `loop()`.
- **`firmware/v1/Unit/`** — Per-flap Arduino Nano firmware. `Unit.ino` (config `#define`s, globals, `setup()`/`loop()`) plus siblings `UnitI2CProtocol.ino` (TWI ISR handlers + address resolution) and `UnitMotion.ino` (stepper motion + hall calibration), split in #175 — same one-TU concat model as the master, with the main sketch (detected by containing `setup()`/`loop()`) placed first. I2C slave whose address is read from four DIP-switch pins (`ADRESSSW1..4`) and offset by `I2C_ADDRESS_BASE` (currently 1) so DIP 0000 → I2C 0x01 (address 0x00 is reserved for general call). Drives a 28BYJ-48 stepper via ULN2003 (`STEPPERPIN1..4`), homes on a KY-003 hall sensor at `HALLPIN`, and applies a per-unit step offset stored in EEPROM (clamped to ±`SFP_OFFSET_LIMIT_STEPS` on both sides of the protocol, #171). The character alphabet is a fixed `letters[]` array in the sketch — the master sends an index, not the character. Calibration (offset / jog / home) and provisioning (#56: EEPROM-stored I2C address via SET/CLEAR_I2C_ADDRESS + IDENTIFY, DIP as fallback — twiboot still listens on the DIP-derived address, so over-I2C reflash requires EEPROM == DIP) are driven from the master's web UI over I2C opcodes.
- **`firmware/v1/UnitBootloader/`** — Vendored + patched [twiboot](https://github.com/orempel/twiboot), an I2C bootloader for the Nanos. Once installed (one-time ICSP flash per unit), the master pushes new unit firmware over I2C from a PROGMEM-bundled hex (no more ICSP cables). See `firmware/v1/UnitBootloader/README.md`.

Master/unit contract: I2C index in the `letters[]` table + speed byte, with `ANSWER_SIZE = 1` status byte back. `UNITS_AMOUNT` (16) in `ESPMaster.ino` is the DIP-switch hardware ceiling and bounds the per-unit state arrays; the effective display width (`displayWidth`, #123) is derived at each bus probe as highest responder + 1 (fallback: the ceiling when nothing responds) and drives all text layout — one image fits any display size 1..16. Units must be DIP-addressed contiguously from 0x01 for the width to match the physical count; `showMessage()` snapshots the width per call because `/reflash-units` can re-probe (and thus mutate `displayWidth`) from a web handler nested inside its yield points.

## Build / Flash / Test Workflow (PlatformIO)

Each sketch has its own `platformio.ini`. Run all commands from the sketch folder.

```bash
pio run                      # build
pio run -t upload            # flash sketch (USB, one-time)
pio device monitor           # serial at 115200
pio test -e native           # host-side unit tests (ESPMaster only)
```

Subsequent master flashes happen via OTA — from this repo: `flashing/ota-master.sh <fw.bin> http://host:port`. The script computes MD5 locally, POSTs to `/firmware/master`, then polls `/settings` for the `sketchMd5` + `lastFlashResult` verdict and prints SUCCESS, EBOOT SILENT REVERT, FLASH CONFIG MISMATCH, or UPLOAD DID NOT REACH HANDLER. Physical re-flash is done from `split-flap-flasher.exe` ("Flash master firmware (USB serial)") — see `flashing/README.md`; the manual `esptool` walkthrough in issue #53 is the fallback.

First-time provisioning of a physical display (programmer bootstrap, twiboot
per Nano, master USB flash, verify) is driven by `split-flap-flasher.exe` —
a PyInstaller one-file exe built by `.github/workflows/flasher.yml` from
`flashing/flasher/` (plain Python package, pytest-covered; dev: `python -m
flasher` from `flashing/` after `make_manifest.py stage`/`collect`; the
`stage` step MUST run between the Unit and ESPMaster builds).

- **ESPMaster** — env `espmaster`, board `esp01_1m`. Library versions pinned in `platformio.ini`. Builtin `EEPROM` is in `lib_deps` because PIO's LDF doesn't surface it by default.
- **Unit** — env `unit` (board `nanoatmega328new`, new bootloader) or `unit_old_bootloader` (board `nanoatmega328`, old bootloader fallback).

Host-side native test env:

- `firmware/v1/ESPMaster/platformio.ini` → `[env:native]` — ESP8266 sketch's pure-logic helpers. Uses `fabiobatsilva/ArduinoFake` to stub `String`, `Print`, etc. Tests in `firmware/v1/ESPMaster/test/test_*/test_main.cpp`.

The ESPMaster env: `ArduinoFake` stubs `map()` as a fakeit mock — each test's `setUp()` must wire in the real Arduino formula via `When(Method(ArduinoFake(Function), map)).AlwaysDo(...)`, otherwise calling `map()` aborts. Other ArduinoFake-mocked globals (e.g. `EEPROM`) are accessed via the `ArduinoFake(EEPROM)` helper macro and should be re-wired in `setUp()` with `When(Method(...)).AlwaysDo([](...) { ... })`.

Python-side tests live in `firmware/v1/ESPMaster/tests/` and cover `build_assets.py` helpers. Run with `python -m pytest tests/` from the `firmware/v1/ESPMaster` directory.

CI: `.github/workflows/build.yml` matrix-builds `v1/ESPMaster`, `v1/Unit`, `v2/Master` and runs both native test envs + the v2 pytest suite. The v2 build's first run on a clean runner is slow (pioarduino hybrid compile downloads IDF).

## Configuration Knobs Worth Knowing

All live as `#define`s at the top of `ESPMaster.ino`:

- `UNITS_AMOUNT` — hardware ceiling (16 = 4-bit DIP addressing), array bound only. The runtime display width comes from the boot probe (`displayWidth`, pure logic in `DisplayWidth.h`, natively tested); never lower this per-display.
- `SERIAL_ENABLE` — toggling this to `true` **disables I2C** on the ESP-01 (shared pins) and with it all unit calls — this doubles as the "ESP standalone" web-UI debug mode (the separate `UNIT_CALLS_DISABLE` knob was removed in #123).
- WiFi has no knob: normal boots try the SDK-persisted credentials for 30 s, then open the `<deviceName>-setup` portal (boot counter cleared on portal entry so it can't trip recovery). The SDK flash sector is the single credential store; `/reset-wifi` erases it. A gitignored `WifiCredentials.h`, if present at build time, is a migration seed only (tried-and-persisted when stored credentials fail).
- `USE_MULTICAST` — enables mDNS. Every network name (hostname, MQTT id/topics, AP SSIDs) derives from the per-device identity: EEPROM `deviceName` if set, else `split-flap-<hex chip id>`; resolved in `resolveDeviceIdentity()` right after the single `initialiseSettings()` call at the top of `setup()` (one `EEPROM.begin` + migration point for every boot path). Static IPs are deliberately unsupported — use DHCP reservation.
- `OTA_ENABLE` — enables Arduino OTA (separate from the web `/firmware/master` path); set `otaPassword` if used.
- `FLAP_AMOUNT` / `AMOUNTFLAPS` — hardware-coupled (45). The master's `FLAP_AMOUNT` and the unit's `letters[]` length must agree.
- MQTT / Home Assistant integration is always compiled in, inert until a broker host is set via the web UI (applied on reboot; password write-only in `/settings`). Entities: HA notification text (show-for-a-dwell then revert, clamp 5–3600 s), Mode select (a mode change from HA or the web UI — or a web message send — cancels an active notification), health telemetry. **MQTT callbacks are LWIP-context: copy + flag only; all work happens in `loopMqtt()`.** Web transients ride the same show-then-revert state (`transientText` + optional `transientDwell` POST fields) and never persist a mode change.

Unit-side: `SERIAL_ENABLE` and `TEST_ENABLE` (cycles a fixed character sequence for homing validation) are commented out by default in `Unit.ino`.

## EEPROM layout

`SettingsEepromLayout.h` carves the master's ESP8266 EEPROM region into named slots — the header itself documents each slot; native tests (`test_eeprom_settings`) enforce the layout invariants (contiguity, bounds, round-trip, migration zero-fill). The rules that must survive any edit:

- New slot ⇒ bump `SETTINGS_VERSION`, extend the `ver < N` migration ladder in `initialiseSettings()` (carve space by shrinking `RESERVED_2`), and end the migration step **before** the version write so `updateSettingsCrc()` stamps a valid checksum. Every `save*()` calls `updateSettingsCrc()` before `EEPROM.commit()`.
- Boot-time blob handling is a pure decision table (`assessSettingsBlob()`, natively tested): blank/foreign magic → defaults; valid CRC → adopt regardless of version byte; CRC mismatch at current/newer version → torn write, defaults + loud log; CRC mismatch at older version → migration ladder. The CRC range is deliberately version-independent so older firmware can validate newer blobs.
- Semantics worth knowing: `deviceName` empty = chip-id default `split-flap-<hex>`; MQTT config applies on reboot and `initMqtt()` must copy into stable Strings (AsyncMqttClient stores raw pointers); MQTT password is write-only (`/settings` exposes only `mqttPasswordSet`, empty submission keeps the stored one); fresh-init timezone default is CE(S)T.

## OTA + recovery

Master flashes go through `/firmware/master` (HTTP POST `multipart/form-data` + `?md5=`): MD5-verified stream to the staging slot, then the **pre-flash sketch MD5** is stashed in RTC memory before reboot. The next boot compares its own `ESP.getSketchMD5()` against the cookie and writes `"ok"` or `"reverted"` (eboot rejected the copy) to `lastFlashResult`; `/settings` surfaces the OTA/boot fields and `flashing/ota-master.sh` turns them into a verdict. This machinery is **v1-only by design** — v2 uses native S3 bootloader rollback instead (see firmware status above).

**Recovery mode** activates on 3 consecutive unhealthy boots (RTC counter, reset after 30 s clean uptime) or remotely via `POST /firmware/recover-mark`. Recovery joins known WiFi if reachable, else SoftAP `<deviceName>-rec`; either way it serves upload-only endpoints (never the setup portal — that's `<deviceName>-setup` on normal boots; quiet-OTA mode is `<deviceName>-ota`). **Gotcha:** in the SoftAP fallback `WiFi.persistent(false)` must precede `WiFi.disconnect()` or the stored station config gets zeroed — the SDK sector is the only credential store. `RtcBootState` (magic-checked, V3-magic migrated in place) holds the boot counter, boot mode, cookie kind, and pre-flash MD5.

## Gotchas

- Editing `.ino` siblings in `firmware/v1/ESPMaster/` is editing one translation unit — declarations and `#define`s from `ESPMaster.ino` are visible everywhere, and order of concatenation is alphabetical by file name. The Arduino preprocessor auto-prototypes plain functions but falls over on templates (`<typeprefixerror>`) and on signatures with namespace-qualified references like `fs::FS&`; add those prototypes manually (header file) rather than relying on auto-prototyping.
- The `.ino`→`.cpp` auto-prototype scanner inserts its prototype block before the first function-shaped match in the merged file — **before** any sibling file's `#include` has appeared. A function whose signature uses library types defined in a later include (e.g. the AsyncMqttClient callbacks in `ServiceMqttFunctions.ino`) needs forward declarations of those types near the top of `ESPMaster.ino` — see the comment block above them there.
- The web UI is in PROGMEM (`WebAssets.h`, regenerated by `build_assets.py` on every build), NOT in LittleFS. No separate `uploadfs` step — editing `data/*.html|js|css` is picked up on the next `pio run`.
- The ESP-01 has very little RAM (~37 KB static free at rest since MQTT became always-compiled in #57). Be conservative adding libraries or large JSON payloads.
- On the async library choice: `dvarrel` forks of `ESPAsyncTCP` + `ESPAsyncWebSrv` are the maintained ESP8266-focused path. `mathieucarbou` is the ESP32 successor; wrong target for ESP-01. Don't "modernize" without measuring.
- The `<DNSServer.h>` + `<ESPAsyncWiFiManager.h>` includes sit deliberately at the very top of `ESPMaster.ino`'s include block to avoid conflicts with the async web server headers — don't "clean up" that include order.
- Test files `#include` the `.ino` sources directly to exercise real code. This means any sibling `.ino` must be compilable standalone in the native env — add explicit forward declarations at the top of a file (e.g. `String cleanString(String);` in `HelpersStringHandling.ino`) if functions are used before their definition in the same file.
- Eboot (the ESP8266 first-stage bootloader) copies from the OTA staging slot into the run slot on reboot. A silent revert — staging write OK, `Update.end(true)` returns success, but the post-reboot sketch is still the old one — is almost always ESP-01 power sag during the erase/write cycle. The `lastFlashResult="reverted"` signal surfaces it; fixing it needs hardware intervention (decoupling caps, beefier supply), not more firmware.
